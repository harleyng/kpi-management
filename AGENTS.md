## Project context

**kpi-management** — the prototype of **Syntra KPI**, a KPI management system built on the
**Balanced Scorecard** (BSC). Goals run on **three tiers — Company → Department → Individual** —
joined by **cascade / link**. Every period is evaluated in **three steps**: the employee
self-assesses with evidence → the manager scores → HR/C&B records the final result. Results feed
a **live dashboard**, ratings and the KPI share of pay.

**This is a product owner's prototype**, built so the product owner and HR can run the whole P1
lifecycle — assign KPIs → enter actuals → evaluate → score → dashboard — and settle the process
before the real build. It is still held to a high engineering standard, because the scoring and
pay rules have to be right before anyone trusts the screens.

| Aspect | Detail |
|---|---|
| Framework | React 18 + TypeScript (`strict`) + Vite (`@vitejs/plugin-react-swc`) |
| UI | shadcn-ui + Tailwind CSS + Radix. White background, primary `#863EEA` |
| Data | **Simulated** — a `DataGateway` contract with a `mock` adapter (in-memory + localStorage, seeded fixtures). **No database yet**; `supabaseGateway` is a stub until Phase 5 |
| Tenancy | **Multi-tenant from day one** — every gateway call takes `tenantId` and filters by it |
| Server state | **TanStack React Query v5** over the gateway, in `src/hooks/queries/*` |
| Client state | **Zustand** (`src/lib/*Store.ts`) + `SessionContext` (simulated tenant, user and role) |
| Auth | **Simulated** — pick a tenant, user and role from the seed; no login |

## Architecture

- **Path alias**: `@/` → `src/`.
- **Layering**: `DataGateway (mock | supabase) → React Query hooks (src/hooks/queries/*) →
  components/pages`. Client state uses Zustand (`src/lib/*Store.ts`).
  - `src/integrations/data/` — **the data layer**: `types.ts` (the contract), `mockGateway.ts`,
    `supabaseGateway.ts` (stub, Phase 5), `index.ts` (`getDataGateway()`, adapter chosen by
    `VITE_DATA_ADAPTER`, default `mock`).
  - `src/integrations/insight/` — the simulated AI assistant behind `getInsightGateway()`.
  - `src/hooks/queries/` — `useQuery` reads with an exported `*Key`, `useMutation` writes that
    `invalidateQueries`. The only layer that calls `getDataGateway()`.
  - `src/lib/` — business rules as **pure functions** (`*Rules.ts`) plus Zustand stores and
    `errorCatalog.ts`. Each rules file has a co-located `*.test.ts`.
  - `src/data/types.ts` — domain types and the **fixed state sets**. `src/data/fixtures/` — the
    seed, which is the **contract between parallel tracks**.
  - `src/contexts/useSession.ts` — the session contract; `SessionContext.tsx` is the provider.
  - `src/pages/` and `src/components/` — `components/ui/` is shadcn, **never edited directly**.
- **Routing**: every route lives in `src/App.tsx` under a single `AppShell`, each page its own
  `React.lazy` chunk. Navigation is defined in `src/components/layout/navConfig.ts` — 5 groups by
  role (plan §7.1). Full route table: `.agents/knowledge/architecture.md`.

## Critical rules

1. **Never `asChild` with `<Button>` + `<Link>`** — it fails to render silently. Use `useNavigate()`.
2. **Statuses come from the fixed sets in `src/data/types.ts`** — Goal Plan, form, cycle, period,
   result and the rest. **Never invent a new label**; add it to the set, its label map and
   `business-rules.md` together.
3. **Every data access goes through `getDataGateway()`** — no component, page or hook imports
   `mockGateway` or `supabaseGateway`.
4. **Every gateway function takes `tenantId` and filters by it.** Never read across tenants. The
   tenant-isolation tests (tenant B must never see tenant A) are what stands in for RLS.
5. **Every calculation lives ONLY in `src/lib/*Rules.ts`** — achievement %, weighted score,
   roll-up, rating, payout %. Pure functions with tests. Never compute in JSX, a hook or the mock.
6. **Error copy comes from `src/lib/errorCatalog.ts`** (ERR-KPI-01…); never retype the strings.
7. **Read with `useQuery` and an exported `*Key`; write with `useMutation` that calls
   `invalidateQueries`.** Query keys start with the tenant.
8. **UI copy is Vietnamese, written inline; code and comments are English.** Do not add an i18n
   library or a `useT()` hook.
9. **Check before creating** — reuse existing rules, hooks and components. New route or page? Follow `.claude/skills/new-page/SKILL.md`. New entity? Follow
   `.claude/skills/add-entity/SKILL.md` (written procedures — there are no slash commands).
10. **A process or business-rule change is not done without its documentation** — update
    `docs/flows/*.md` and `.agents/knowledge/business-rules.md`. Changing a flow means following
    `.claude/skills/update-flow/SKILL.md` as a written procedure.
11. **Fixtures in `src/data/fixtures/` are the contract between tracks** — changing them (or the
    `DataGateway` contract) after Gate 1 is a **Large** change: `system-architect` reviews it and
    every other track is told.

## Branches and commits

**Work goes to `main`.** The repository owner is **@harleyng**. No pull requests are needed.

1. Commit in **conventional commit** style: `type(scope): description` (e.g. `feat(goals): add weight check`).
2. Push to `main`: `git push origin main`.
3. **Parallel tracks** (Phase 2, T1–T7): each track works in its **own git worktree**
   (`git worktree add ../kpi-<track> -b track/<track>`), and tracks merge into `main` in the order
   of plan §6.3 — **T1 → T2 → T7 → T3 → T4 → T5 → T6** — each merge passing the Phase 4 gate.

## Development workflow (MANDATORY)

**Full details: `.agents/workflows/development.md`**

Every task runs through **four phases**; its size decides which phases apply and who is involved:

| Size | Examples | Phases | Experts |
|---|---|---|---|
| **Trivial** | Typo, copy tweak | 3 + 4 | QA |
| **Small** | One bugfix, one added field | 1 (self) → 3 → 4 | QA |
| **Flow / Spec** | Changing a business rule, a step in a process, writing a new user story | 1 → 2 → 3 → 4 | `cpo` + `ba-expert` → the relevant domain expert → QA |
| **KPI Rules** | Touching `src/lib/*Rules.ts`, a calculation method, scoring, roll-up, rating, payout | 1 (self) → 2 → 3 → 4 | `hr-performance-expert` + `qa` → QA |
| **Workflow** | Touching the form state machine, steps, SLA / overdue, return, proxy, delegation, launches | 1 (self) → 2 → 3 → 4 | `workflow-expert` + `system-architect` → QA |
| **Medium** | A new component, a feature change | all four | `cpo` → `cto` + `ui-ux` → QA |
| **Large** | A new module, a cross-cutting feature, a contract or fixture change | all four | `cpo` + `ba-expert` → `cto` + `ui-ux` + `system-architect` → QA |

**Key rules:**
- When in doubt, treat it as **Medium**.
- **Phase 4 is always required**: `npm run typecheck && npm run test && npm run build && npm run lint`
  — all four green. **Unlike OmniX Studio, tests are a gate here**: `src/lib` computes scores and pay.
  `npm run lint` is also enforced by CI.
- Do not skip to coding without analysis (Medium and above).
- The user can override: "skip the analysis" = Trivial; "full analysis" = Medium/Large.

### Resolving disagreements (apply in order)

1. **User outcome beats technical elegance** — the CPO beats architectural purism.
2. **Business correctness beats visual polish** — the plan, the sources and the BR beat aesthetics.
3. **On a tie, pick the simpler option.**
4. **Prefer the option that is easier to reverse** — this is a prototype for settling a process;
   changing your mind is a feature.
